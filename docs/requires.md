# パーソナル情報収集エージェント 要件・構成方針

## 1. 目的

日々の情報収集、蓄積、検索、深掘りを支援する個人向けエージェントをAzure上に構築する。

会話や検索の履歴から新しい情報収集対象を提案し、ユーザーの承認を経て収集対象を拡張できるようにする。

本プロダクトは個人検証を兼ねる。プレビュー機能の利用や、実装中の方式検証を許容する。

## 2. 決定した構成方針

| 項目 | 方針 |
|---|---|
| エージェント実装 | Microsoft Agent Framework（MAF）で実装する |
| エージェントのデプロイ先 | Microsoft FoundryのHosted Agent |
| Foundry・モデルのリージョン | East US 2 |
| 情報検索基盤 | サーバーレスのFoundry IQ |
| Foundry IQのリージョン | 東日本（Japan East） |
| ナレッジグラフ | トピックグラフを採用する |
| インデックスへの取り込み | Blobを情報源とするpull型 |
| 原本の保存先 | Azure Blob Storage |
| 生成アーティファクト | HTMLファイルとしてBlobに保存する |
| 収集対象一覧・メタデータ | Azure Cosmos DBのサーバーレス構成 |
| 定期収集 | Azure Functionsで毎朝6時（日本時間）に実行する |
| 対話中の外部情報検索 | Web検索を利用できるようにする |
| 音声対話 | Voice LiveとHosted Agentの連携で実現する方針 |
| ネットワーク | 閉域構成は不要。パブリックエンドポイントの利用を許容する |

※パブリックエンドポイントの利用は、データを匿名公開することを意味しない。
※リージョン・SKU・モデル・プレビュー機能の組み合わせは、実装時に検証する。

## 3. エージェントの役割

MAFで検索・調査・承認などの処理をオーケストレーションする。

主な機能は以下とする。

- 蓄積済みの情報資産をFoundry IQから検索する。
- トピックグラフを使って関連テーマや幅広い根拠を取得する。
- 必要に応じて通常検索で詳細な根拠を取得する。
- Web検索で最新情報や未収集の情報を補完する。
- 調査結果を回答する。
- 必要に応じてHTMLレポートを生成し、Blobに保存する。
- 会話・検索履歴から新しい収集対象を提案する。
- ユーザーが承認した対象のみ、収集対象一覧に登録する。

## 4. 定期情報収集

### 4.1 実行タイミング

- 毎朝6時（日本時間）にAzure Functionsを起動する。

### 4.2 処理の流れ

1. Cosmos DBから有効な情報収集対象一覧を取得する。
2. 指定された情報源から情報を収集する。
3. 収集した情報の原本をBlobに保存する。
4. 原本の保存先や収集結果などのメタデータをCosmos DBに保存する。
5. Blobを情報源とする取り込み処理で、Foundry IQのコンテンツインデックスを更新する。
6. トピックインデックスの更新・再生成を行う。

### 4.3 検証事項

- 収集完了後にインデックス取り込みを開始する連携方法。
- 原本の形式と、検索用に必要なテキスト化・正規化。
- 新規・更新・重複・削除の扱い。
- 収集失敗時のリトライと再実行。
- トピックインデックスの更新・再生成方法。

トピックインデックスの更新頻度や自動化方式は、現時点では固定せず、個人検証の中で決定する。

## 5. 検索・深掘り

### 5.1 トピックグラフの用途

トピックグラフは、トレンドや全体要約だけでなく、深掘りする際の関連情報の探索にも利用する。

### 5.2 深掘りの基本フロー

1. トピックグラフ検索で関連する観点と根拠を広く取得する。
2. 取得した情報から、深掘りする論点を整理する。
3. 論点ごとに通常検索を実行し、詳細な根拠を取得する。
4. 必要に応じてWeb検索で情報を補完する。
5. 出典を付けて回答する。
6. 必要に応じてHTMLレポートを生成する。

単純な事実確認では通常検索を使うなど、質問に応じて検索経路を選択する。

### 5.3 検証事項

- サーバーレスのFoundry IQでトピックグラフを利用できるか。
- トピックグラフ検索の設定をリクエスト単位で制御できるか。
- 特定トピックやその配下に絞った検索が可能か。
- トピックグラフ検索と通常検索を組み合わせた場合の品質・遅延・コスト。
- 日々の情報追加がトピック構造にどう反映されるか。

## 6. 保存するデータ

### 6.1 Azure Blob Storage

- 収集した情報の原本。
- エージェントが生成したHTMLアーティファクト。
- 必要に応じて、検索用に加工したデータ。

収集原本と生成アーティファクトは、用途を分けて管理する。

### 6.2 Azure Cosmos DB

- 情報収集対象一覧。
- 収集した情報のメタデータとBlobへの参照。
- 会話ログ。
- Web検索ログ。
- 新しい情報収集対象の候補。
- 候補の承認・却下状態。

### 6.3 Foundry IQ

- 原本から取り込んだ検索用コンテンツ。
- コンテンツインデックス。
- トピックインデックス。
- エージェントから利用するナレッジソース・ナレッジベース。

## 7. 情報収集対象の提案と承認

### 7.1 基本フロー

1. 会話ログやWeb検索ログを分析する。
2. 継続的に収集すると有益な情報源を候補として抽出する。
3. 候補と提案理由をユーザーに提示する。
4. ユーザーが承認した場合のみ、Cosmos DBの収集対象一覧に追加する。
5. 追加した対象を、以降の定期収集に含める。

### 7.2 原則

- エージェントの判断だけで収集対象を追加しない。
- 承認対象を明確にし、承認した候補と登録内容を対応付ける。
- 重複候補や却下済み候補の扱いを定義する。

### 7.3 未決定事項

- 候補抽出を会話ごとに実行するか、定期バッチにするか。
- 承認をチャット、画面、その他の方法で行うか。
- 候補の再提案条件。
- 収集可能性や利用条件の確認方法。

## 8. 音声対話

### 8.1 構成方針

- MAFで実装したHosted AgentにVoice Liveを接続する。
- 調査・検索ロジックと音声入出力を分離する。
- まずテキスト対話で検索・深掘りを検証し、その後に音声対話を追加する。

### 8.2 想定する利用体験

- 音声で情報収集や調査を依頼する。
- 回答を聞いた後、「その点を詳しく」などの追加質問で深掘りする。
- 詳細な出典やHTMLレポートは画面で確認する。

### 8.3 検証・設計事項

- East US 2でのVoice Live・Hosted Agent・モデルの対応組み合わせ。
- 音声連携機能の提供状況と制約。
- 会話文脈の保持。
- 長時間の調査を待たせずに扱う方法。
- 読み上げ用の短い回答と、画面用の詳細回答の分離。
- 音声認識の誤りを考慮した承認方法。
- 音声原本と文字起こしの保存方針。

## 9. その他の未決定事項

- Web検索に利用するツールと、検索ログの取得方法。
- HTMLアーティファクトの閲覧・認証方法。
- Cosmos DBのコンテナ構成、パーティションキー、TTL。
- リソース間の認証・権限設計。
- Functions、Blob、Cosmos DBなどの配置リージョン。
- 日米間通信による遅延と転送コスト。
- 監視、エラー通知、利用量・コストの上限。
- 外部コンテンツのプロンプトインジェクション対策。
- 生成HTMLの安全性対策。
- 生成レポートを検索基盤に再投入するかどうか。

## 10. 検証の進め方

1. East US 2にFoundry・モデル・Hosted Agentの実行環境を用意する。
2. 東日本にサーバーレスのFoundry IQを用意する。
3. 少量の原本をBlobに保存し、pull型の取り込みを検証する。
4. トピックグラフの作成・検索・更新を検証する。
5. MAFで通常検索・トピックグラフ検索・Web検索を組み合わせる。
6. HTML生成とBlob保存を実装する。
7. 毎朝6時の定期収集を実装する。
8. 収集対象の提案・承認・登録を実装する。
9. Voice Liveを接続し、音声対話を検証する。

トピックグラフが利用できない、または更新方式に制約がある場合も、
通常検索を先に動かし、グラフ部分を独立して検証できる構成にする。
